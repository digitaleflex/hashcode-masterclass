MODULE 02 · TYPESCRIPT · PARTIE 01

Types fiables

  • unknown est plus sûr que any pour une donnée inconnue.
  • Une assertion as User ne transforme ni ne valide la donnée.
  • Les types devraient rendre les états invalides difficiles à représenter.
  • Séparer modèle métier, DTO et données persistées.
À retenir / mise en pratique
Frontière recommandée : donnée inconnue → validation → logique métier.
MODULE 02 · TYPESCRIPT · PARTIE 02

Unions discriminées

  • Un champ status ou kind identifie la variante.
  • TypeScript réduit le type après un test de discriminant.
  • never aide à repérer les branches oubliées.
  • Les états loading/success/error évitent les combinaisons incohérentes.
À retenir / mise en pratique
Exemple : type Result = {status:'ok'; data:User} | {status:'error'; message:string};
MODULE 02 · TYPESCRIPT · PARTIE 03

Génériques

  • Les génériques préservent la relation entre entrée et sortie.
  • extends contraint les opérations disponibles.
  • Les valeurs par défaut peuvent simplifier une API.
  • Ne pas généraliser un code sans bénéfice concret.
À retenir / mise en pratique
Créer une fonction qui retourne le même type précis que son argument.
MODULE 02 · TYPESCRIPT · PARTIE 04

Types conditionnels et mappés

  • T extends U ? X : Y choisit un type selon une condition.
  • infer extrait un type dans une branche conditionnelle.
  • keyof extrait les clés d’un type.
  • Pick, Omit, Partial et Record sont utiles, mais ne remplacent pas un modèle lisible.
À retenir / mise en pratique
Les types récursifs trop complexes peuvent ralentir la compilation.
MODULE 02 · TYPESCRIPT · PARTIE 05

Validation runtime

  • Valider les entrées réseau, formulaires, fichiers et variables d’environnement.
  • Un schéma comme Zod peut valider puis inférer un type.
  • Normaliser et valider sont deux opérations différentes.
  • Les erreurs ne doivent pas révéler de données sensibles.
À retenir / mise en pratique
Atelier : modéliser un résultat, valider un payload inconnu et traiter chaque variante.
MODULE 02 · TYPESCRIPT · PARTIE 06

Configuration et évaluation

  • Activer strict et corriger les erreurs plutôt que multiplier les assertions.
  • Séparer les types publics des types internes.
  • Tester les comportements à l’exécution.
  • Évaluer précision, lisibilité et robustesse des contrats.
À retenir / mise en pratique
Maîtrise : types précis et frontière runtime clairement validée.
